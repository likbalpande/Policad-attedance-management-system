The main backend PB.
The real-time attendance marking part is only handled by LAG / LALS.

The PB has RBAC. Every API checks for the permission. 
For each API, a unique permission identifier is kept in a constants file.
There will be a bypass mechanism in the validation middleware based on role an action.
This will again be maintained in a constant file.
The super-admin will be directly created in DB.
There will be no signup api.

The login api will remain same for super-admin / admin / faculty.
It will be OTP based login.
The access token only lives for 15 minutes. Then, it is renewed on expiry but within 7 days.
The only condition to renew is that login_count in DB should match the login_count in payload.
The access token (JWT) will be done using asymmetric hashing. 
The access token hash the data with private key.
The data (payload) will have a "origin" key which has value as hash (it will be created using UAI).
The public key will be shared to other micro-services via API request by validating the service communication secret.

The login of student will happen through one time password generated while user creation (version: 1).
As soon as the password is used, the random hard password will be created and placed in its place.

Admin / Faculty with P_O can create a new password for the student.
When ever the new password is generated, 
    <user_id>,<old_password_version> is saved in the banned_access table.
    Every server downloads this list and saves it in memory. 
    Server refetch it every two minutes (for created at < 2 days).
    The password_version is updated +1.

The access token creation for student will hash the data against private key.
The data (payload) will have a "origin" key which has value as hash (it will be created using UAI).
The access token only lives for 1 day. Then, it is renewed on expiry but within 30 days.
The only condition to renew is that password_version in DB should match the password_version in payload.

For the session, the admin / faculty will start the attendance session using FTF/FTA.
It can only start the session if there is no ongoing entry in "attendance_session_records" (< 2 minutes from now).
FTF/FTA will send the request to PB. PB will authenticate it, validate the course_id, access_level and then generate 120 tokens.
i-th token is a hash of timestamp (in seconds) (i second ahead of now) + course_id + session_id + secret.
The secret will be generated at 12am everyday for each organization and then stored in the DB.
Whenever server starts, it will pull that secret from the DB for each organization.
Whenever a session is requested, the attendance_session_records will be inserted with course_id, session_id, user_id, session_start_timestamp, created_at.
Response from the server will ~ look like { "course_id":"...", "session_id", "...", hashes: { "ith-timestamp":"hash", ...} }

It will create three new entries in the ACLS_task_queue table which actually acts like a queue.
The entry will have the scheduled_at timestamp as +50 seconds, +100 seconds, +150 seconds.
It will also have course_id, session_id, has_processed: false, is_processing: false, processing_started_at: null, created_at, retires: 0.
If course_id, session_id pair already exists and the has_processed is false, then 
    If the count of already present entries = 3
        the latest present entry will be updated to set scheduled_at timestamp as +0 seconds from now.
        remaining two entries will be updated for +50 & +100 seconds.
        a new entry will be created for +150 seconds.
    If the count of already present entries = 2 then 
        the latest present entry will be updated to set scheduled_at timestamp as +0 seconds from now.
        already existing other entry will be updated to +50 seconds from now 
        and remaining entries will be created.
    If the count of already present entries = 1 then 
        the present entry will be updated to set scheduled_at timestamp as +0 seconds from now.
        and remaining entries will be created.

For is_ongoing_attendance_session API, it will check if there is a entry in attendance_session_records which has session_start_timestamp < 110 seconds from now.
If yes, then it will create 120 tokens as per that session_start_timestamp, else send empty response.
i-th token is a hash of timestamp (in seconds) (i second ahead of session_start_timestamp) + course_id + session_id + secret.
Response from the server will ~ look like { "course_id":"...", "session_id", "...", hashes: { "ith-timestamp":"hash", ...} }

The PB will have a cron which runs every 10 seconds to check if anything is pending and invokes ACLS for that.
PB can put the new entry in table scheduled_at timestamp +0 second, by the faculty's or admin's manual trigger.
(Note: the FTA/FTF request should be at_least 1 minute greater than the last scheduled job or error will be returned "too early : wait for 1 minute.")
If there exists an unprocessed entry, then it will update the closest one by timestamp.

ACLS will take the course_id, session_id and the get all the from dynamoDB corresponding to it.
It will get the final status of student present / absent.
It will get all the students of the course / event and then remaining from the dynamoDB data will be marked absent.
This snapshot of data will be stored in the attendance table in postgreSQL.
Then it will call the AWLS with (with course_id, session_id).
Attendance table would have user_id, course_id, session_id, status, remark, ip_address, device_info (json), marked_at, created_at. 

The FTF/FTA will render the QR corresponding to each hash for each timestamp.
The FTS will scan the QR and simultaneously store the scanned timestamp, session_id, course_id, hash value will be stored in FTS memory.
Once the number of hashes = 5, the list will be sent to LAG along with scanned timestamps, session_id, course_id. 

LAG will generate a timestamp on server corresponding to the request.
LAG will validate the user access (JWT) using the public key. 
It will get the public key from PB via API call by sending secret of communication.
That public key will be cached for 5 minutes.
LAG will validate if the scanned timestamp (highest one) is at max 5 seconds old than the server's timestamp.
It will also check if the highest - smallest timestamp <= 7 seconds.
*** It will then check the course_id is valid or not, and get the other details if required.
The request will be given to LALS with 
    hashes (with scanned timestamps), 
    course_id, user_id, session_id, ip_address
    secret (org specific), org's webhook url and alias data.
Note: alias data is basically the data which admin has aliased for user_id, course_id, session_id.
The alias mapping will be stored in a separate table in pg specific to org.

LALS will verify each hash for correctness by recreating the hash with scanned timestamp + course_id + session_id + secret.
If all the hashes are correct then it will check if the `{course_id}_{session_id}_{user_id}` pair already exists in dynamoDB 
and if not, then it will create a new entry as array with an object containing ```remark: "QR Based Attendance", status: "present", scanned_timestamp: "...", ip_address, created_at: "..."```
Then it will call the PB webhook without await (with course_id, session_id, user_id, remark: "QR Based Attendance", status: "present", scanned_timestamp: "...", ip_address, created_at: "...").
Then it will return the success response to LAG.
The LAG will then send success response to the frontend.

AWLS accept the request and send response of accepted.
It will get all student for the course_session from pg "attendance" table.
Then it will await the webhook url array of (with course_id, session_id, status, user_id, remark, scanned_timestamp, created_at and aliases) for all students.
If it receives 2XX status code then it will put it in processed webhooks table `{course_id}_{session_id}_{user_id}` with all payload.
If it receives any other status code then it will put it in failed webhooks table `{course_id}_{session_id}_{user_id}` with all payload.
(Note: If record already exists then replace.)

PB webhook will be exposed with a service communication secret, where the given information will be processed,
to send SSE to all connected Admins / Faculties of that course_id.

FTA / FTF can mark the student as present / absent manually.
It will directly create / update the entry `{course_id}_{session_id}_{user_id}` in the dynamoDB.
It will have ```remark: "Admin triggered - {user_id}", status: "absent", scanned_timestamp: null, created_at: "..."```.
Note that the value object will be pushed as a new item in the array.
It will the call AWLS (with course_id, session_id, user_id, remark: "Admin triggered - {user_id}", status: "absent", scanned_timestamp: "...", created_at: "...", org's webhook url, alias data)
Then it will send SSE to all connected Admins / Faculties of that course_id.

FTA / FTF will have two views for each session in the course:
    Live view where 
        it calls is_ongoing_attendance_session
            if it return hashes then 
                it shows QR 
                    sorted by timestamp, changing every second
                it shows all the students 
                    If there exists some data in attendance table in postgreSQL, 
                    then they will be marked present / absent as per their status.
                    Others will be shown as "yet to mark".
                    As it receives the info from SSE, it will update the attendance status of the students.
                    It will also refetch to get attendance table (pg) records every 10 seconds 
                        and the unique students marked present in db but "yet to mark" on UI will be updated to present.
            if it return empty then
                a button is shown to start attendance session
    Report view
        it will show the attendance stats as per the pg_table.
        the data will be re-fetched on page refresh only.
        if there is any pending / unprocessed entry for the course_id + session_id in the ACLS_task_queue
        then a corresponding notice will be shown "A processing is scheduled to happen in X+15 seconds. Please wait till then."
        Where X is the scheduled_at timestamp for the task.
