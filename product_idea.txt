The main backend PB.
The real-time attendance marking part is only handled by LAG / LALW.

The PB has RBAC. Every API checks for the permission. 
For each API, a unique permission identifier is kept in a constants file.
There will be a bypass mechanism in the validation middleware based on role an action.
This will again be maintained in a constant file.
The super-admin will be directly created in DB.
There will be no signup api.

The login api will remain same for super-admin / admin / faculty.
It will be OTP based login.
The access token only lives for 15 minutes. Then, it is renewed on expiry but within 7 days.
The only condition to renew is that login_count in DB should match the login_count in payload.
The access token (JWT) will be done using asymmetric hashing.
The access token hash the data with private key 1.
The data (payload) will have a "origin" key which has value as hash (it will be created using UAI).
This hash will again be a asymmetric hash. It will be done using private key 2.
The public key 1 & 2 will be shared to other micro-services via API request by validating the service-communication-secret.

The login of student will happen through one time password generated while user creation (version: 1).
As soon as the password is used, the random hard password will be created and placed in its place.

Admin / Faculty with P_O can create a new password for the student.
When ever the new password is generated, 
    password_generated_at field is updated in users table.
    The password_version is updated +1.
    Every server downloads the list  of users with password_generated_at < 2 days and saves it in memory (say users_on_alert_map). 
    Server refetch it every 5 minutes.

The access token creation for student will hash the data against private key.
For access token validation in api call, it will check from users_on_alert_map that user id exists or not.
If it exists then password version in payload should match that in the map.    
The data (payload) will have a "origin" key which has value as hash (it will be created using UAI).
The access token only lives for 1 day. Then, it is renewed on expiry but within 30 days.
The only condition to renew is that password_version in DB should match the password_version in payload.

For the session, the admin / faculty will start the attendance session using FTF/FTA.
It can only start the session if there is no ongoing entry in "attendance_session_records" (< 2 minutes from now).
FTF/FTA will send the request to PB. PB will authenticate it, validate the course_id, access_level and then generate 120 tokens.
i-th token is a hash of timestamp (in seconds) (i second ahead of now) + course_session_id + secret.
The secret will be generated at 12am everyday for each organization and then stored in the DB.
Whenever server starts, it will pull that secret from the DB for each organization.
Whenever a session is requested, the attendance_session_records will be inserted with course_id, session_id, user_id, session_start_timestamp, created_at.
Response from the server will ~ look like { "course_session_id", "...", hashes: { "ith-timestamp":"hash", ...} }

For is_ongoing_attendance_session API, it will check if there is a entry in attendance_session_records which has session_start_timestamp < 110 seconds from now.
If yes, then it will create 120 tokens as per that session_start_timestamp, else send empty response.
i-th token is a hash of timestamp (in seconds) (i second ahead of session_start_timestamp) + course_id + session_id + secret.
Response from the server will ~ look like { "course_session_id", "...", hashes: { "ith-timestamp":"hash", ...} }

For attendance_marked_webhook API, it will see all the connected admins / faculties for the given course_session_id and then send SSE to them. 
It will also store the `${course_session_id}_${user_id}` and status in recent_attendance_cache for quick access.

For get_attendance_status API, the user will only send the user_id and course_session_id, 
    if it is present in recent_attendance_cache, then that status will be returned
    otherwise it will fetch all values for that course_session_id, store them in cache and then return the status for user_id.
    The status can be 'present', 'absent' or null.
    The TTL for keys in cache will be 10 seconds.

The FTF/FTA will render the QR corresponding to each hash for each timestamp.
The FTS will scan the QR and simultaneously store the scanned hash value, timestamp, course_session_id will be stored in FTS memory.
Once the number of hashes = 10, the list will be sent to LAG along with scanned timestamps, course_session_id. 

It will wait for the response from LAG and 
    then poll PB "get_attendance_status" at 5s, 15s, 30s, 60s, 75s, 90s, 105s, 120s - for status.
    It will keep polling until it gets status == 'present'.

LAG will generate a timestamp on server corresponding to the request.
It will get the public key 1 & 2 from PB via API call by sending secret of communication.
That public keys will be cached for 5 minutes.
LAG will validate the user access (JWT) & UAI using public key 1 & 2. 
LAG will validate count(scanned hashes) == 10.
LAG will validate if the scanned timestamp (highest one) is at max 9 seconds old than the server's timestamp.
It will also check if the highest - smallest timestamp <= 14 seconds.
*** It will then check the course_session_id is valid or not, and get the other details if required.
The request will be given to SQS --> LALW with 
    hashes (with scanned timestamps), remark: "QR Based Attendance", status: "present"
    course_id, course_session_id, user_id, ip_address, device_config,
    secret (org specific), org's webhook url and alias data.
Note: alias data is basically the data which admin has aliased for user_id, course_id, course_session_id.
The alias mapping will also be stored in a pg.

In LALW,
    If status == "present" then 
        LALW will verify each hash for correctness by recreating the hash with scanned timestamp + course_session_id + secret.
        If the hashes are correct then it will put an entry in db, in attendance_history 
            - (user_id, course_session_id, remark, status, device_config, ip_address, scanned_at)
            returning attendance_history_id.
        If the session_id, user_id pair exists in attendance table then it will replace else create - with same data.
            returning attendance_id.
        If the org has kept live_attendance_trigger true, then it will call the webhook url with the alias data.
            If it receives 2XX status code then it will considered as processed else failed.
            The data will be stored in webhook_history table. 
        It will call the PB webhook "attendance_marked_webhook" with service-communication-secret to tell course_session_id, user_id, status.
    If status = "absent" then
        It will put an entry in db, in attendance_history 
            - (user_id, course_session_id, remark, status, device_config:null, ip_address:null, scanned_at: null)
            returning attendance_history_id.
        If the session_id, user_id pair exists in attendance table then it will replace else create - with same data.
            returning attendance_id.
        If the org has kept live_attendance_trigger true, then it will call the webhook url with the alias data.
            If it receives 2XX status code then it will considered as processed else failed.
            The data will be stored in webhook_history table. 
        It will call the PB webhook "attendance_marked_webhook" with service-communication-secret to tell course_session_id, user_id, status.

FTA / FTF can mark the student as present / absent manually.
The request will be given to SQS --> LALW with 
    hashes (with scanned timestamps), remark: "Admin triggered", status: "absent", remarked_by_user_id,
    course_id, course_session_id, user_id,
    secret (org specific), org's webhook url and alias data.




FTA / FTF will have two views for each session in the course:
    Live view where 
        it calls is_ongoing_attendance_session
            if it return hashes then 
                it shows QR 
                    sorted by timestamp, changing every second
                it shows all the students 
                    If there exists some data in attendance table in postgreSQL, 
                    then they will be marked present / absent as per their status.
                    Others will be shown as "yet to mark".
                    As it receives the info from SSE, it will update the attendance status of the students.
                    It will NOT refetch. Admin can refetch manually.
            if it return empty then
                a button is shown to start attendance session
    Report view
        it will show the attendance stats as per the pg_table.
        the data will be re-fetched on page refresh only.
