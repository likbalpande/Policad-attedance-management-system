BUG FIXED DURING PASS 1: zod's `.default(false)` on a boolean schema field
makes react-hook-form's `useForm<z.infer<...>>()` fail to compile (RHF's
Resolver needs the schema's input/output types to match exactly, `.default()`
breaks that). Fixed by dropping `.default()`, relying on RHF's own
`defaultValues` instead.

FOLLOW-UP 2: SHARED FE<->BE API CONTRACTS (same session, user feedback)

User asked whether request/response shapes were enforced as shared types
between FT and PB. Answer: no - every FT type was hand-typed by reading PB's
DTOs/row types at write time, no compiler link. Notable: `@platform/types`'s
own `index.ts` already had a comment anticipating exactly this ("FT<->PB API
shapes ... get added here as those features are built") but it had never
actually been done, for this session's work or the prior session's
staff-login types.

Presented 3 options (A: full shared response+request types with PB return-
type annotations; B: share only Zod request DTOs; C: process-rule-only, no
restructuring). User rejected C, wants both A and B combined: Zod request
DTOs shared and validated by PB / inferred by FT, AND shared response types
so "whatever PB sends and whatever FT expects are provably the same type."
Confirmed scope: retrofit the 5 resources already built this session, not
just apply going forward.

MECHANISM BUILT:
- `@platform/types` gained a `zod` dependency and now holds, per resource
  (mirroring PB's own module tree): the Zod request DTO + inferred type, and
  a plain-TS response entity type. Barrel-exported from index.ts as before.
- PB's `dto/*.dto.ts` files became one-line re-exports from `@platform/types`
  (dto/ folder stays as the place to look, definition now centralized).
  Route-param-only DTOs (batch-id, permission-config-group-id, remove-
  access-identifier params) stay PB-local - no FE-constructed payload there.
- Every response-producing PB service function's return type is now
  explicitly annotated against the shared entity type (e.g.
  `Promise<Organization>`). Real discovery mid-implementation: PB's DAL rows
  have `Date` objects for timestamps, but the wire/shared type needs `string`
  (what FT actually receives post-JSON) - so this literally would not
  compile without also formatting dates. Added one `utils/serialize-<x>.ts`
  per module (organizations, users/sanitize-user.ts already existed and got
  adapted, access-identifiers, permission-config-groups, batches) that
  converts Date->ISO-string, making the Promise<T> annotation actually true
  rather than just structurally hopeful.
- Also caught and fixed two latent (harmless but real) type inaccuracies
  surfaced by this exercise: batches' create/update/delete responses don't
  include the `access` roster (only list/get do, via resolveBatchAccess) -
  previously typed as one `Batch` interface requiring `access` always; now
  split into `Batch` (bare) and `BatchWithAccess extends Batch` (list/get) in
  @platform/types. And FT's delete.api.ts was typed as returning `null`, but
  PB's delete endpoint actually returns the deleted batch row - fixed to
  `Batch`.
- FT's RHF form schemas were deliberately kept FE-local (not replaced by the
  shared Zod object) - PB's schema rejects `""` for an optional URL field,
  which every create-dialog's empty-field UX already depends on tolerating.
  The enforcement point is the submit handler's constructed payload, typed
  against the shared DTO.
- batches/access-identifiers/permission-config-groups' local AccessRosterUser/
  FacultyAccessRosterUser/BatchAccess interfaces (previously duplicated
  PB-side in batches.access-roster.service.ts and FT-side in
  batches.types.ts) collapsed into the one shared @platform/types definition.

BUG FOUND AND FIXED DURING VERIFICATION: `pnpm -r run typecheck` failed
across every PB module touching a shared DTO - `@platform/types`'s zod
resolved to a *different installed version* (3.25.76, pulled in because FT
already depended on that range) than `@platform/http`/platform-backend's zod
(3.23.8), so the actual Zod schema *values* crossing from `@platform/types`
into PB's `validate()` middleware were structurally near-identical but
nominally distinct classes - classic pnpm dual-instance issue. Fixed by
pinning `@platform/types`'s zod dependency to the exact same version PB uses
(`"3.23.8"`, not a caret range) and reinstalling; confirmed via `readlink -f`
on each package's resolved `node_modules/zod` that PB/http/types now share
one physical install while FT keeps its own newer zod (fine, since FT only
ever imports the shared package's *type*, never the schema value).
