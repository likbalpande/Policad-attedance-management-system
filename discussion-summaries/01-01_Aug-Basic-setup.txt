PART 2: Code architecture & setup
-----------------------------------
Existing (empty) scaffold found in repo:
   platform/apps/{frontend, platform-backend, live-attendance-gateway,
   live-attendance-lambda-worker}
   platform/packages/  (empty)

Decisions made:

1. Monorepo tooling
   - Package manager: pnpm (fast, disk-efficient, strict dependency resolution,
     mature compat with Prisma + Capacitor - avoid yarn Berry/PnP for this stack).
   - Task orchestrator: none for now (plain pnpm workspace scripts). Revisit
     Turborepo later if build/dev-loop pain shows up - not worth the setup cost
     yet with only 4 apps and an empty packages/.

2. LALW deployment model
   - Hybrid: Express app + SQS consumer loop locally (against LocalStack in
     Docker); real AWS Lambda (SQS-triggered) in production.
   - Requires decoupling business logic from the runtime shell:
       core/consumer logic (process one message) is framework-agnostic and
       shared between both entrypoints.
       local/server.ts -> Express shell (health check only) + SQS long-poll
       loop calling the shared consumer logic.
       lambda/handler.ts -> real AWS Lambda entrypoint (exports.handler over
       SQSEvent.Records), calling the same shared consumer logic.
   - Local SQS emulation: LocalStack (Docker-based AWS emulator; also covers
     future needs like S3 for org logo uploads).
   - Production Lambda is purely event-driven - NO HTTP surface in prod.
     Express is confined to the local/ dev shell only, not a prod dependency.

3. Shared packages/ contents
   - packages/types - cross-service contracts (PB<->LAG, LAG<->LALW SQS
     payload, LALW<->PB webhook payload, FT<->PB API shapes).
   - packages/permissions - permission-identifier constants + P_O/P_B/P_C
     types, used by both PB (RBAC checks) and FT (conditional UI rendering).
   - packages/uai - UAI-generation logic (ua-parser-js based). MUST be shared
     identically between FT (client-side "origin" hash) and PB/LAG
     (verification) - any drift breaks login.
   - packages/crypto - asymmetric sign/verify helpers shared between PB
     (signs) and LAG (verifies), keeping algorithm/padding choices in sync.
   - packages/db - SHARED schema + client + migrations only (infra layer).
     ORM CHANGED from Prisma to Drizzle - see PART 3, item 1.
   - packages/dal - the ONLY package allowed to import packages/db and run
     queries against it. Every app (PB, LALW, and LAG if it ever needs DB
     access) calls into packages/dal's repository functions - no app talks
     to the DB directly. See PART 3, item 3.
   - packages/http - ApiSuccessResponse/ApiErrorResponse, error classes,
     asyncHandler, Zod validation middleware, generic error-handling
     middleware. Shared across PB/LAG (and LALW's local health-check shell).
     See PART 3, item 4.
   - packages/logger - Winston logger instance factory, so every service's
     entry/exit/error logs look identical, tagged with a different `service`
     name per app. See PART 3, item 4.
   - packages/tsconfig, packages/eslint-config - shared compiler/lint config
     across all 4 apps.
   - Workspace package naming convention: @platform/<package-name>
     (e.g. @platform/db, @platform/dal, @platform/http, @platform/logger,
     @platform/types, @platform/permissions, @platform/uai, @platform/crypto).

4. Common backend layering concepts (PB / LAG / LALW) - SUPERSEDED for PB,
   see PART 3. Originally proposed as one identical flat-layered shape for
   all three services (routes/controllers/services/repositories/...). This
   was revisited in PART 3 once PB's actual resource count was considered:
   PB now uses a feature/module-based structure instead. LAG (thin, no DB
   access per the idea) and LALW (message-driven, no routes/controllers at
   all) still fit a flat/minimal shape. Shared concepts that survived across
   all three regardless of layout:
   - Validation library: Zod (TS-first, infers static types from schemas,
     composes well with packages/types).
   - Controllers kept as a separate layer from routes (routes stay pure path +
     middleware wiring; services stay framework-agnostic and easier to unit
     test without mocking Express req/res).
   - No app owns its own DB access code - see packages/dal above and PART 3.

5. LALW's structural difference from PB/LAG
   Keeps services/validators/utils/errors layers (calls @platform/dal for
   any DB access, same as every other app - no local repository files).
   Replaces routes/controllers/app.ts/server.ts with:
     consumer/process-message.ts - the SQS-equivalent of a controller:
       takes one parsed SQS message, calls services/ in order. This is the
       single piece both entrypoints below call into.
     local/server.ts - Express shell + SQS long-poll loop (LocalStack) in dev.
     lambda/handler.ts - real AWS Lambda entrypoint in prod.


PART 3: PB folder structure (reconciling platform-backend/backend-folder-structure-prompt.txt)
--------------------------------------------------------------------------------------------
Found an existing prompt file at
platform/apps/platform-backend/backend-folder-structure-prompt.txt (written
before this discussion). It conflicted with PART 2 decisions in a few ways;
resolved as follows and the file itself was rewritten to match.

1. ORM: SWITCHED from Prisma to Drizzle (+ drizzle-kit for migrations).
   Reason: matches the prompt file's original intent, and Drizzle has a
   notably better cold-start/bundle-size story for LALW's Lambda than
   Prisma's engine binary. packages/db was Prisma in PART 2 - that's now
   outdated, packages/db is Drizzle.

2. PB folder paradigm: feature/module-based, NOT the flat layered structure
   from PART 2 item 4. Reason: PB is by far the largest app (organizations,
   users, batches, courses, sessions, tags, permissions, attendance,
   webhooks, ...) - a flat routes/controllers/services/ shape would flatten
   into noisy folders holding 15+ unrelated files each. LAG and LALW are
   thin enough that this doesn't apply to them.

   PB structure:
     platform/apps/platform-backend/
       src/
         app/
           <module-name>/
             <module-name>.routes.ts
             dto/<method>-<module-name>.dto.ts   (zod schema, TS type inferred)
             controllers/<module-name>.<controller-name>.controller.ts
             services/<module-name>.<service-name>.service.ts
                 -> calls @platform/dal functions, never touches the DB
                    client directly
         constants/
         middlewares/     - PB-specific only (e.g. RBAC/permission-check
                             middleware against @platform/permissions).
                             Generic error/validation middleware now lives
                             in @platform/http instead of being local.
         utils/             - PB-specific helpers only
         config/env.config.ts
         types/
         logger/              - thin wrapper: createLogger({ service:
                                  'platform-backend' }) from @platform/logger
         app.ts                 - register middlewares + routers
         server.ts                - load env, init DB connection, create
                                     express app, start server

3. Shared centralized DAL (bigger change than PART 2's per-app
   repositories/ idea): NO app may talk to the DB directly, only through
   @platform/dal. Split into two packages, not one:
     packages/db  - schema + Drizzle client + migrations only (infra layer)
     packages/dal - repository functions, organized by resource, the ONLY
                    package allowed to import packages/db and query it.
                    PB, LALW, and (if ever needed) LAG all call into this,
                    never into packages/db directly.
   This replaces the earlier per-module repository/ folder idea inside PB
   entirely - services/ call @platform/dal, full stop.

4. New shared packages formalized (were only "candidates" in PART 2):
     packages/http   - ApiSuccessResponse/ApiErrorResponse, error classes,
                        asyncHandler, Zod validation middleware, generic
                        error-handling middleware. Used by PB, LAG, and
                        LALW's local health-check shell.
     packages/logger - Winston logger instance factory (entry/exit/error
                        logging convention, tagged by `service` name).
   These came from the prompt file's own item 14 suggestion ("these can go
   in common packages").

5. Other conventions carried over from the prompt file (kept, no conflict):
   - Functional programming style; classes only for specific cases (error
     classes, logger class, etc.)
   - API response convention:
       success: { success: true, message, data }
       error:   { success: false, message, errors? }
   - Standard middleware stack per HTTP-serving app: cors, helmet,
     express.json, cookie-parser, morgan.
   - Health check endpoint "/health".
   - No mandatory test setup right now, but code must be written so tests
     can be added later without restructuring (keep services framework-
     agnostic, avoid tightly coupling logic to Express req/res).
   - .env: one file shared across dev/prod, distinguished via an identifier
     inside it (not separate .env.development / .env.production files).

PART 5: Build tooling switch + application-level enum typing
-----------------------------------------------------------------
1. Build tooling: switched every package/app's `build` script from `tsc -p
   tsconfig.json` to `tsup` (esbuild-based, much faster) with a `prebuild`
   script running `tsc --noEmit` first, so type errors still block the build
   even though esbuild itself doesn't type-check. Required adding
   platform/.npmrc with `enable-pre-post-scripts=true` - pnpm does not run
   `prebuild` automatically otherwise (verified this empirically before
   relying on it). Packages build with --dts (consumed as libraries); PB's
   app build (`tsup src/server.ts ...`) doesn't need --dts (it's an
   executable). dev scripts (tsx watch) unaffected.

2. Application-level enum columns now use Drizzle's `.$type<T>()` instead of
   plain untyped varchar, so table-structure.txt's `// application_level_enum
   (...)` columns get compile-time safety without becoming real Postgres
   enums (deliberately not DB-enforced, per PART 1 item 17's reasoning
   applied consistently). New package @platform/enums created to hold the
   non-permission vocabularies (COURSE_TYPE, ATTENDANCE_STATUS,
   ATTENDANCE_REMARK, WEBHOOK_STATUS) - kept separate from @platform/
   permissions (which stays RBAC-only: PERMISSION_SCOPE, USER_ROLE) since
   course type / attendance status aren't permission concepts. packages/db
   now depends on both permissions and enums purely for these type
   annotations - confirmed via a regenerated migration that this has zero
   effect on generated SQL (identical DDL with vs. without). Columns updated:
   admin_access_identifiers.type, admin_permissions_config_groups.type,
   admin_permitted_access_identifiers.type, users.role, courses.type,
   attendances.status/remark, attendance_history.status/remark,
   webhook_history.status.
   Side effect: this let us delete the `as "super_admin" | "admin" |
   "faculty"` casts in PB's auth.login.service.ts / auth.refresh.service.ts.
   Removing the cast in auth.refresh.service.ts surfaced a real gap - unlike
   login(), refresh() never explicitly rejected role === student, so the
   stricter type didn't compile until that check was added. Fixed as
   defense in depth (refresh() now throws before issuing a token for a
   student role, matching login()'s guard).

PART 6: DB connection pooling - PB only
-----------------------------------------
@platform/db's createDbClient and @platform/dal's initDal now take an
optional DbClientOptions ({ max?, idleTimeoutSeconds?, connectTimeoutSeconds? }).
Default max is 1 (no real pooling) - deliberate default, not just an
oversight: LALW's production Lambda handler is per-invocation (each
concurrent invocation is a separate process), so a wide pool per invocation
would multiply connections against Postgres's connection limit rather than
reuse them. Only PB - a genuinely long-running server - opts into a real
pool, via a new DB_POOL_MAX env var (default 10) passed to initDal in
server.ts. When LALW is built later, it must call initDal with no options
(or explicit { max: 1 }), never a pool. Also backfilled .env.example, which
had gone stale (was missing the JWT/origin PEM key vars from PART 4).

PART 7: is_deleted filtering convention in packages/dal
-----------------------------------------------------------
Found an inconsistency: organizations.repository.ts's listOrganizations
filtered is_deleted=false but findOrganizationById/findOrganizationByName
did not; users.repository.ts filtered nowhere at all, meaning a soft-deleted
(deactivated) admin/faculty could still log in and refresh tokens via
auth.login.service.ts / auth.refresh.service.ts. Fixed: every function in
both repositories (reads and writes) now filters eq(<table>.isDeleted,
false) by default - "deleted" means "doesn't exist" for every normal
caller, enforced centrally in the DAL rather than left to every service to
remember. A future admin-restore/audit feature needing deleted rows should
get its own explicitly-named function, not change this default. is_archived
is a separate concept (still active/visible) and was deliberately left
alone - nothing in the spec defines archived-filtering behavior yet.

PART 8: OpenTelemetry / distributed tracing
-----------------------------------------------
New @platform/tracing package: initTracing({service, otlpEndpoint?}) (OTel
Node SDK bootstrap, OTLP exporter with a ConsoleSpanExporter fallback when
no endpoint is configured - deliberate, so tracing works with zero new infra
today and swaps to any OTLP-compatible backend later via one env var, no
code change), withSpan() (manual span helper), injectTraceContext()/
extractTraceContext() (W3C tracecontext propagation primitives, for the
future SQS boundary).

Key technical finding: OTel's Node auto-instrumentation patches modules at
require()-time, so express/http must not be required anywhere before
initTracing() runs, or instrumentation is a silent no-op (no error, spans
just never appear). A static `import` gets hoisted above runtime code by
TS/bundlers, so PB's entrypoint was restructured: new src/instrumentation.ts
(calls initTracing() then `void import("./server")` - a genuinely deferred
dynamic import) is now the real entrypoint everywhere (package.json
dev/build/start), src/server.ts unchanged otherwise. Verified empirically:
a GET /health request produces one full trace (HTTP span + every Express
middleware as a child span + route handler span, all one traceId).

Second finding: the `postgres` driver we use (not `pg`) has no official
OpenTelemetry auto-instrumentation package, and drizzle-orm 0.33 has no
built-in OTel integration either. So @platform/dal wraps every repository
function in withSpan() manually instead (db.<table>.<fnName> span names,
db.system/db.sql.table attributes) - verified working via a standalone
script (span appears in console output with correct attributes).

@platform/logger now stamps trace_id/span_id onto every log entry when
called from inside an active span (reads @opentelemetry/api's active
context via @platform/tracing's getActiveTraceContext()) - verified: a log
call inside withSpan() gets both fields, a log call outside any span gets
neither.
[SUPERSEDED by PART 9 item 1 - this custom injection was deleted in favor of
@opentelemetry/instrumentation-winston doing it automatically. getActiveTraceContext()
itself outlived that as unused dead code until PART 10's cleanup removed it too.]

Not done yet (LAG/LALW don't exist as code): wiring initTracing() +
injectTraceContext()/extractTraceContext() into LAG and LALW so the
LAG -> SQS -> LALW -> PB webhook flow becomes one trace instead of three
disconnected ones. The primitives exist in @platform/tracing now so this is
ready when those apps get built - both must use the same dedicated-
entrypoint pattern as PB (LALW's lambda/handler.ts especially, since
Lambda's execution model makes the init-order rule just as important there).
Also not decided: which OTLP backend to actually point at (self-hosted
collector/Jaeger/Tempo vs. a SaaS vendor) - not blocking, console exporter
works fine for now.

PART 9: OpenTelemetry refinements (asked "is there a more elegant way")
-----------------------------------------------------------------------------
Reviewed PART 8's implementation for genuine improvements rather than just
defending it. Four applied, one tried and reverted:

1. Deleted @platform/logger's custom trace_id/span_id injection code
   entirely. Verified (the hard way - got a false negative first by
   requiring winston before initTracing() in a throwaway test, same
   require-order mistake the whole init-order rule warns about) that
   @opentelemetry/instrumentation-winston, already loaded via
   getNodeAutoInstrumentations(), does the exact same trace-context
   injection automatically with zero code on our side. @platform/logger no
   longer depends on @platform/tracing at all.

2. getNodeAutoInstrumentations() was loading 39 instrumentation packages
   unconditionally (mongodb, redis, graphql, grpc, kafka, mysql, oracledb,
   hapi, koa, socket.io, pg [wrong driver - we use `postgres`], ...) -
   real startup/bundle cost, worst for LALW's future Lambda cold start.
   Explicitly disabled the ~33 we'll never use; kept http, express, winston,
   aws-sdk, aws-lambda (LALW), undici (future outbound fetch e.g. webhook
   dispatch). Verified exactly 6 active instrumentations at runtime.

3. Added spanProcessorMode: "batch" (default) | "simple" to initTracing().
   BatchSpanProcessor (the SDK default) is a known bad fit for Lambda -
   execution environments freeze between invocations, so a timer-based
   flush may never fire and spans get silently dropped. LALW must use
   "simple" when built. Not urgent (LALW doesn't exist) but cheap to design
   in now rather than redo later.

4. withSpan() no longer sets SpanStatusCode.OK on success - only on error.
   Matches OTel convention (successful spans stay UNSET; OK is for
   deliberately overriding what would otherwise look like an error).

5. TRIED AND REVERTED: a tracedQuery(table, fn) higher-order wrapper meant
   to derive each DB span's name from the wrapped function's own .name
   (via a named function expression) instead of a hand-typed span-name
   string, to remove the (minor) risk of the string drifting from the
   function name. Implemented it, then hit tsup's TS2742 (.d.ts can't
   portably name a type inferred through a generic function call assigned
   to a const) - fixing it required an explicit type annotation on every
   export, duplicating each function's signature a second time. Net more
   repetition than the problem it solved, so reverted to the plain
   `export async function xxx() { return withSpan("db.users.xxx", ...) }`
   pattern from PART 8. Worth remembering if this idea resurfaces - it
   looks appealing but isn't actually a win once you hit the dts-generation
   wall.

PART 10 - Refresh token rotation + dropped passwordVersion in favor of loginCount
   1. REFRESH TOKEN ROTATION: refresh() previously only reissued the access
      token; the refresh token kept its original absolute TTL from login, so
      even an actively-used session got hard-logged-out once that TTL
      elapsed. Fixed: refresh() now returns a freshly-issued refresh token
      too (same payload, new TTL) on every call - a sliding window. Inactive
      sessions still expire after TTL of no activity; active ones don't.
   2. DROPPED passwordVersion, students now use loginCount (same field/check
      as staff). Reasoning, in order of the actual discussion:
      - Original ask: "isn't passwordVersion the same as loginCount?" No -
        loginCount bumps on every login (kills prior sessions, single active
        session model); passwordVersion only bumped on password change
        (allowed concurrent sessions across a password's lifetime).
      - Real requirement surfaced: students must NOT have concurrent
        sessions at all (anti account-sharing for attendance marking) - so
        the "allow concurrent sessions" behavior of passwordVersion was
        actually wrong for students, not just differently named.
      - passwordVersion's real value was the per-request users_on_alert_map
        design (product-idea.txt, pre-edit) - near-real-time revocation on
        password reset, cheap because password resets are rare/independent
        of whether a user currently holds a live token, so the map stayed
        small.
      - Considered reusing that same alert-map idea keyed by "recently
        logged in" for the new concurrent-session check - rejected: holding
        any live token already implies a recent login (that's the only way
        to get one), so "recently logged in" would match ~100% of active
        users on any given day. Not a filter at all, just a slower way to
        check everyone.
      - Refined to keying the map by CONCURRENT login detection instead:
        added users.last_login_at (all roles). On login, if the previous
        last_login_at is still within the access-token TTL window, a prior
        session could still be alive - genuinely rare (one login/day is
        normal), so a map of just these entries stays small and actually
        targets the sharing scenario, unlike a raw recency map.
      - Scope decision: build the PB-side data (last_login_at column,
        loginCount bump + lastLoginAt stamp in incrementLoginCount, password
        reset also bumps loginCount atomically via SQL) now. The actual
        per-request alert-map ENFORCEMENT has to live on the
        attendance-marking path (LAG), which doesn't exist as code yet -
        left as documented future work, not half-built today. Until LAG
        enforcement exists, a concurrent student session is only caught at
        the stale session's next refresh (bounded by student access token
        TTL, 1 day per spec) - not instant.
   3. Changes: users.password_version column dropped, users.last_login_at
      added (nullable, timestamptz). StudentAccessTokenPayload.passwordVersion
      -> loginCount (packages/types). updateUserPassword DAL fn dropped its
      passwordVersion param, now atomically increments loginCount via
      drizzle's sql`` template (no read-then-write - straightforward single
      UPDATE, no race to introduce). incrementLoginCount DAL fn now also
      stamps lastLoginAt = now() on every call (used by both staff and,
      later, student login). Migration 0000 regenerated in place (still the
      only migration, same day, no deployed data) - same geography(Point,
      4326) quoting bug hit again, same manual fix applied. product-idea.txt
      and table-structure.txt updated to match; the old users_on_alert_map
      paragraph rewritten to describe the concurrent-login design and
      explicitly flag the LAG-side enforcement as future work.
   4. Deleted @platform/tracing's getActiveTraceContext() - dead code, zero
      callers anywhere. It survived PART 9 item 1 (which deleted the
      logger-side code that used to call it) as an orphaned primitive with a
      now-inaccurate doc comment still claiming @platform/logger used it.
      injectTraceContext()/extractTraceContext() in the same file were left
      alone - unused too, but have a real documented future consumer
      (LAG/LALW SQS propagation), unlike this one.
