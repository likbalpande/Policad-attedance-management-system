KEY FINDING:
platform-backend already has programmatic OTel instrumentation via
@platform/tracing's initTracing(), called explicitly from
src/instrumentation.ts (the real entrypoint per package.json scripts). This
differs from the generic NODE_OPTIONS="--require .../register" pattern in
the user's snippet, which is the env-var-driven *auto*-instrumentation
approach. Of the 6 env vars supplied, only 2 actually do anything here:
  - OTEL_EXPORTER_OTLP_ENDPOINT - already read by env.config.ts
  - OTEL_EXPORTER_OTLP_HEADERS - not passed explicitly to OTLPTraceExporter
    in init.ts, so the OTel SDK auto-falls-back to reading it from
    process.env itself for auth
The other 4 (OTEL_SERVICE_NAME, OTEL_EXPORTER_OTLP_PROTOCOL,
OTEL_TRACES_EXPORTER, OTEL_NODE_RESOURCE_DETECTORS) are no-ops given the
current manual-construction code path, and NODE_OPTIONS --require would
double-instrument if added alongside the existing initTracing() call - so
none of those 4 were added.

Also found: OTLPTraceExporter's `url` config is used as-is with no
`/v1/traces` suffix auto-append (that only happens when the SDK builds the
URL itself from the bare env var, not when `url` is passed explicitly as
init.ts does). Grafana's gateway needs that suffix for trace ingestion.

USER DECISION LOCKED IN:
Fix the /v1/traces suffixing in code (packages/tracing/src/init.ts) rather
than baking the full signal-specific path into the .env value - keeps
OTEL_EXPORTER_OTLP_ENDPOINT spec-compliant as a base URL, future-proofs for
metrics/logs exporters later.

FOLLOW-UP 2 - LOGS EXPORT (WINSTON -> OTLP):
User noticed Grafana showed "connected" but Logs view was empty. Root
cause: only traces were ever wired up; no OTel logs pipeline existed at
all. @opentelemetry/instrumentation-winston (already active via
getNodeAutoInstrumentations, not in the DISABLED list) does log
correlation (trace_id/span_id injection) by default, but log SENDING is a
silent no-op without both (a) a registered LoggerProvider and (b) the
@opentelemetry/winston-transport package, which was not installed anywhere
in the repo.

Researched via 1 Explore agent (packages/logger's winston setup + init
ordering, instrumentation-winston's actual send-vs-correlate behavior by
version, NodeSDK's logRecordProcessors config support, and which OTel log
packages were already present transitively) before proposing the fix -
confirmed init order is already correct (winston is only ever require()'d
downstream of instrumentation.ts's deferred `import("./server")`, after
initTracing() has run).

USER DECISION LOCKED IN:
No ConsoleLogRecordExporter fallback when otlpEndpoint is unset (unlike
traces) - winston's own Console transport already prints formatted JSON
logs locally; an OTel console dump on top would just duplicate every line
in a rawer format.
