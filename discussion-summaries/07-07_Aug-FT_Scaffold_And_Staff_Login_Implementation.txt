TWO REAL BUGS FOUND AND FIXED DURING LIVE BROWSER TESTING (not caught by
typecheck/lint/build - both were runtime-only):

1. Blank page, zero console output, zero errors. Root cause: Vite serves
   pnpm-linked `@platform/*` workspace packages (built CJS via tsup) through
   `/@fs/` as source, which skips Vite's CJS->ESM named-export interop -
   `import { USER_ROLE } from "@platform/permissions"` failed at runtime with
   "does not provide an export named 'USER_ROLE'", which is an ESM linking
   error (not a thrown exception), so nothing in main.tsx's module graph ever
   executed and nothing was logged anywhere. Fix: added
   `optimizeDeps.include: ["@platform/permissions", "@platform/types",
   "@platform/uai"]` to vite.config.ts, forcing them through esbuild's
   pre-bundler. Documented in the architecture skill's FT section - any new
   @platform/* dep FT adds needs the same treatment.

2. Wrong-role redirect race: an authenticated faculty account hitting
   /super-admin bounced through /login before landing on /staff, instead of
   going straight to /unauthorized. Root cause: `createBrowserRouter` fires
   loaders for the initial route as soon as the router object is
   *constructed* (not when RouterProvider mounts), and React Router v7 runs
   parent/child loaders in parallel, not parent-then-child - so an async root
   loader awaiting Capacitor Preferences does not reliably finish before a
   child route's synchronous requireRole check reads the store. Fix:
   restructured main.tsx to await session rehydration first, then
   dynamically `import("./App")` (and therefore routes/router.tsx) only
   after - so the store is already correct before the router (and its
   loaders) exist at all. Removed the now-unnecessary root loader/
   HydrateFallback complexity from router.tsx. Documented in the architecture
   skill.

POST-VERIFICATION REFACTOR (user-prompted):
User asked why api/ wasn't split one-file-per-endpoint and grouped by actor,
given it'll grow. Noted PB itself already splits one-file-per-action (not
per-resource) for its controllers/services (auth.staff-login.controller.ts,
auth.refresh.controller.ts, ...), so FT's flat auth.api.ts/auth.queries.ts
(3 functions in 2 files) didn't match that precedent. Actor-grouping stays
exactly as already decided (only for genuinely single-actor resources -
auth is used by 3 actors via one shared endpoint, so it doesn't qualify).
Agreed structure: resource becomes a **folder** once it has >1 action, split
by individual endpoint within, mirroring PB's controller/service split.
Refactored api/auth.api.ts + api/auth.queries.ts (2 files) into api/auth/
(5 files: request-otp.api/queries.ts, staff-login.api/queries.ts, refresh.api.ts
- no .queries.ts for refresh, only called from lib/auth-refresh.ts's
interceptor, never a user-triggered mutation). Updated all 3 consumer imports
(email-step-form.tsx, otp-step-form.tsx, lib/auth-refresh.ts) and
frontend-setup.txt's api/ section to document the per-endpoint-file rule for
every future resource. Re-verified typecheck/lint/live browser render after.
