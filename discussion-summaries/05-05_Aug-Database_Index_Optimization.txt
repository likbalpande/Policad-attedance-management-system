DATABASE INDEX OPTIMIZATION - 2026-08-05

OBJECTIVE:
Find all database queries in @platform/dal, identify missing indexes, and add them to optimize performance.

ANALYSIS PERFORMED:
1. Scanned all 7 repository files (access-identifiers, batches, organizations, permission-config-groups,
   permitted-access-identifiers, user-permissions, users)
2. Documented 34 queries across all repositories
3. Identified current index state: only 3 indexes exist (in users, user_permissions, attendances tables)
4. Analyzed WHERE clauses, JOIN conditions, and soft-delete filtering patterns

KEY FINDINGS:
- USERS table: 10+ queries with no soft-delete filtering indexes
- BATCHES table: 5 queries completely unindexed
- ORGANIZATIONS table: 4 queries with no index support
- USER_PERMISSIONS table: RBAC join queries lack FK column indexes
- PERMISSION_CONFIG tables: Group membership queries unindexed

INDEXES ADDED: 12 total (refined after feedback)
- Users (4): email, identifier+orgId, role+isDeleted, role+orgId+isDeleted
- Batches (2): orgId+isDeleted, id+orgId
- Organizations (1): name (id covered by PK)
- User Permissions (2): userId, adminPermissionsConfigGroupId
- Admin Permitted Access Identifiers (1): permissionConfigGroupId+accessIdentifierId
- Admin Access Identifiers (1): type
- Admin Permissions Config Groups (1): type

USER FEEDBACK INCORPORATED:
1. "Having isDeleted in every index doesn't make sense; it can be filtered after index scan"
   - User was right: isDeleted filter is O(1) after index seeks on id/email
   - Storage overhead: Each index gets fatter unnecessarily

2. Refined approach: Keep isDeleted ONLY in range/list query indexes
   - idx(role, isDeleted) - role list can have many rows, filtering helps
   - idx(orgId, isDeleted) - batch list can have many rows, filtering helps
   - Removed from: id, email, name lookups (all specific, filter is fast)

3. Removed redundant PK index: idx__organizations__id
   - PostgreSQL automatically indexes primary keys
   - Removed unnecessary duplicate to save storage

4. Rationale: Early-stage optimization - minimal deleted data today, revisit if bloat becomes issue

DESIGN DECISIONS:
1. Include isDeleted ONLY in composite indexes for range/list queries (role, orgId filters)
2. Exclude isDeleted from single-value lookups (id, email, name) - filter after seek is fast
3. Preferred composite indexes over separate single-column indexes to reduce bloat
4. Column order in composites follows query WHERE clause order for optimal selectivity
5. Kept existing idx__user_permissions__resource_type__resourceId (different query pattern)
6. Added FK column indexes to optimize join traversal in RBAC checks
